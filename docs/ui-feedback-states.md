# System Feedback & States — حياة

وثيقة مخصصة لرسائل وسلوك حالات الواجهة، منفصلة عن صفحات الوظائف.

## لماذا كل نوع؟

| النوع | متى يُستخدم؟ | مثال | مكان التنفيذ |
|---|---|---|---|
| Toast | نجاح سريع لا يحتاج مسارًا جديدًا | تم تحديث البيانات | `Hayat.toast(...)` |
| Inline alert | خطأ/توجيه داخل نموذج | البريد مستخدم مسبقًا | `Hayat.alertForm(...)` |
| Field error | خطأ في حقل معين | كلمة المرور قصيرة | `Hayat.fieldError(...)` |
| Confirmation dialog | عملية تحتاج تأكيدًا | هل تريد تسجيل الخروج؟ | `Hayat.confirmDialog(...)` عبر SweetAlert2 المحلي |
| Full-screen state | تفعيل/استعادة أو حالة خطأ | تم تفعيل الحساب | `status.html?type=...` |
| Empty state | لا توجد بيانات | لا توجد طلبات حاليًا | ضمن الوحدة المرتبطة |
| Loading | أثناء حفظ/تحقق أو تحديث | جارٍ تسجيل الدخول / تحميل البيانات | تعطيل الإرسال، أو LoadingSkeleton مع `aria-busy` |

## حالات منفذة

| الحالة | النوع | الرابط / المحفز |
|---|---|---|
| تسجيل الخروج بنجاح | Toast لمدة 3 ثوانٍ | تحويل مباشر إلى `login.html` بعد التأكيد؛ مرة واحدة دون تكرار عند التحديث |
| تأكيد البريد بنجاح | Full-screen | `status.html?type=verified` بعد إدخال الرمز التجريبي |
| إعادة تعيين كلمة المرور | Full-screen | `status.html?type=reset` |
| الوصول غير المسموح | Full-screen | `status.html?type=denied` |
| الصفحة غير المتاحة | Full-screen | `status.html?type=missing` |
| تعذّر العملية مؤقتًا | Full-screen | `status.html?type=error` أو `type=temporary-error`؛ إجراء للمحاولة أو العودة |
| رمز تحقق خطأ/منتهي | Inline | `verify.html` |
| أخطاء التسجيل | Field + Inline | `register.html` |
| إعادة إرسال رمز تجريبي | Toast | `verify.html` |
| موظف ينتظر تفعيل بريده | StatusBadge + Verify | `pending_activation` بعد إضافته؛ الدخول يفتح التحقق التجريبي |
| تعديل طلب نشط | Modal + Toast | حقول Tabler وسبب محفوظ في التدقيق؛ تُحفظ المدخلات عند الخطأ |
| إيقاف إداري لطلب | تأكيد مع السبب | `cancelled` مع الفاعل والوقت، دون منح المدير إجراء الاستيفاء |
| تأكيد تبرع مكتمل | تأكيد + Toast + إشعار للمتبرع | سجل ونقاط وتدقيق وإشعار في كتابة واحدة، مع منع التكرار |
| تصحيح إداري | تأكيد مع السبب + إشعار للمتبرع | -5 واحدة، وحفظ الأصل؛ الإجراء غير متاح للمؤسسة |

## حالات أُضيفت مع وحدات v0.2
- طلب دم منشور بنجاح.
- تم قبول الطلب / رفض الطلب.
- بعد القبول: «بانتظار التنسيق» مع بطاقة الطلب الحالي وزر «التراجع عن الاستجابة»؛ النداءات الأخرى مخفية مؤقتًا.
- فتح طلب آخر أثناء التنسيق: حالة «لديك استجابة جارية» ورابط للطلب الحالي؛ لا أزرار قبول لطلب ثانٍ.
- التراجع: نافذة تأكيد ثم تحديث الحالة وإعادة النداءات المطابقة؛ يبقى متاحًا بعد تغيير الملف أو التوفر.
- التنسيق المنتهي: حالة محفوظة في الردود دون إعادة أزرار القبول لاستجابة انتهت بتوثيق التبرع.
- لا يوجد متبرعون مطابقون.
- لا توجد إشعارات أو سجل تبرعات.
- لا توجد نتائج بحث.
- تم توثيق التبرع، أُضيفت +5 نقاط.
- محاولة تأكيد التبرع مرتين.
- تأكيد إلغاء طلب أو إيقاف موظف.
- طلبات مخفية أثناء التنسيق تبقى محفوظة. إشعارات النقاط الشخصية التي لا تتبع طلبًا تُعرض بصورة مستقلة، وتؤدي إلى السجل أو حركات النقاط.
- انقطاع الاتصال، واستعادة الاتصال والمزامنة: **مؤجل إلى تنفيذ PWA الحقيقي**، ولا يُدّعى وجوده في v0.2.

## قواعد تصميم الرسائل
- عنوان قصير ودقيق، تفصيل مفيد، وإجراء تالي واضح عند الحاجة.
- لا يظهر رمز تجريبي كأنه بريد تم إرساله بالفعل: صندوق البريد التجريبي يوضح أنها محاكاة.
- تجنب كشف ما إذا كان بريد مسجّلًا في صفحة استعادة كلمة المرور في النص العام.
- لا نستخدم صفحات نجاح كاملة لكل حفظ صغير. التفعيل والاستعادة لهما شاشة نجاح. وفق ملاحظة المستخدم، الخروج إشعار مختصر يختفي تلقائيًا في صفحة الدخول.
- المسار القديم `status.html?type=logout` محفوظ للتحويل. لا يظهر صفحة خروج ثابتة، ولا ينهي جلسة فعالة لمجرد فتح الرابط.
- النوافذ التي تطلب سببًا أو تحرير بيانات تستخدم Tabler؛ التأكيدات العامة تستخدم SweetAlert2. تظهر رسائل الأخطاء بالعربية، ولا يُمسح الإدخال الصحيح عند فشل الإرسال.
- لا تُحرّك النماذج أو الجداول. يحترم التحميل والرسوم والعدادات `prefers-reduced-motion`، وتبقى القيم والجداول البديلة متاحة. نتائج التحقق الفعلية في [ACCEPTANCE_TESTS.md](ACCEPTANCE_TESTS.md).
