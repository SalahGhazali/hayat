# Hayat – حياة | وثيقة مواصفات النموذج التفاعلي (Frontend MVP)

**الإصدار:** 1.0 (خط أساس للمراجعة قبل البرمجة)  
**الحالة:** المتطلبات المتفق عليها مثبتة، والتفاصيل التي تحتاج اعتمادًا موضحة صراحة.  
**التقنيات المقررة للنسخة التجريبية:** HTML5, CSS3, Vanilla JavaScript  
**مرجع التوثيق:** *Smart Blood Donation Management Platform (Hayat) – Graduation Project* (تقرير مشروع التخرج، 39 صفحة)، لا سيما الأقسام 1.3 و1.4 و3.2 و3.4 و3.5.  

> **توضيح المصطلح:** المقصود هنا بـMVP هو **نموذج واجهات وتفاعلات شامل** يمثل رحلة الاستخدام في النظام الحقيقي، وليس نسخة إنتاجية فيها قاعدة بيانات أو خادم. كل العمليات بين الحسابات على أجهزة مختلفة، وإرسال الرسائل الحقيقية، والصلاحيات المؤمنة على الخادم، تنتظر التطوير الفعلي.

## 1. هدف المنصة وحدود عملها

منصة حياة تنسّق بين بنوك الدم والمتبرعين: تسجيل المتبرعين، إنشاء الطلبات، ترشيح المتبرعين حسب الفصيلة والموقع والتوفر الأولي، استقبال الردود، توثيق التبرع الفعلي، وعرض السجلات والتقارير. 

**خارج نطاق المنصة وفق التقرير:** الفحوصات المخبرية، تحري الأمراض، اختبار التوافق النهائي مع المريض، نقل الدم السريري، إدارة التخزين المادي لأكياس الدم، المدفوعات، وأجهزة المستشفيات. القرار الطبي النهائي للجهة الطبية المختصة. **قبول طلب التبرع ≠ إجراء التبرع ≠ صلاحية وحدة الدم للنقل إلى مريض.**

## 2. الأدوار والصلاحيات (قرارات معتمدة)

هناك **ثلاثة أدوار رئيسية**: `DONOR`، `BLOOD_BANK`، `SYSTEM_ADMIN`.

داخل دور `BLOOD_BANK` يوجد تمييز إداري بين:
- **الممثل الرسمي (Official Representative):** ينشئه مدير النظام مع المؤسسة، ويملك جميع صلاحيات تشغيلها، بالإضافة إلى **إضافة موظفي مؤسسته وإدارتهم**.
- **موظف بنك الدم (Blood Bank Staff):** ينشئ حسابه الممثل الرسمي، وله **نفس صلاحيات التشغيل** مثل الممثل، لكن **لا يدير الموظفين**.

لا يوجد دور رابع باسم *Health Supervisor*؛ التقارير الرقابية تقع في لوحة `SYSTEM_ADMIN`، وتُقدَّم للجهات الصحية المخوّلة حسب نطاق البيانات المسموح.

| الوظيفة | Donor | Bank Staff | Official Rep. | System Admin |
|---|:---:|:---:|:---:|:---:|
| إدارة ملفه الشخصي | ✓ | ✓ | ✓ | ✓ |
| عرض الطلبات الموجّهة وقبولها/رفضها | ✓ | — | — | — |
| إنشاء الطلبات وإدارتها | — | ✓ | ✓ | رقابة/تدخل إداري موثّق حسب السياسة |
| البحث عن متبرعين مرشحين | — | ✓ | ✓ | حسب السياسة |
| توثيق تبرع فعلي | — | ✓ | ✓ | — |
| عرض تقرير المؤسسة | — | ✓ | ✓ | ✓ |
| إضافة/تعطيل موظفي المؤسسة | — | — | ✓ | رقابة إدارية حسب السياسة |
| إنشاء مؤسسة وممثلها الرسمي | — | — | — | ✓ |
| إدارة مستخدمي المنصة وتقارير الإشراف | — | — | — | ✓ |

**قيود إلزامية:** يرتبط كل موظف بمؤسسته؛ لا يستطيع التعامل مع مؤسسة أخرى أو ترقية نفسه أو الوصول إلى صلاحيات System Admin. العمليات المهمة تسجّل الفاعل والوقت والجهة.

## 5. المسارات الأساسية التي يجب أن تعمل في نموذج الـMVP

### A. تسجيل متبرع جديد
1. يفتح المستخدم `Register`.
2. يدخل الاسم والبريد والهاتف وكلمة المرور والتأكيد والفصيلة (يسمح بـ«لا أعرف») والمدينة والمنطقة؛ الموقع الدقيق وتاريخ آخر تبرع اختياريان.
3. يتحقق JavaScript من اكتمال المدخلات وتناسقها وعدم تكرار الهاتف/البريد **داخل بيانات النموذج المحلية**.
4. تُحاكى مرحلة `pending_verification`، ثم يظهر رمز تحقق **تجريبي داخل النموذج**؛ عند نجاحه تصبح الحالة `active`.
5. يفتح حساب Donor. في النسخة الحقيقية سيُرسل الرمز بالبريد وتُنفّذ جميع التحققات الحساسة على الخادم.

### B. إنشاء بنك دم وإدارة موظفيه
1. System Admin ينشئ المؤسسة وممثلها الرسمي.
2. الممثل يسجل دخول المؤسسة، ويفتح `Staff Management`، ويضيف الموظفين.
3. يرتبط الموظفون بالمؤسسة نفسها؛ لهم صلاحيات التشغيل ذاتها دون زر إدارة الموظفين.
4. يتعقب النظام من أنشأ الحساب ومَن نفذ كل إجراء.

### C. طلب دم من بنك الدم
1. موظف المؤسسة ينشئ طلبًا بفصيلة ووحدات وأولوية ونطاق بحث.
2. النظام التجريبي يرشّح المتبرعين من بيانات وهمية وفق الفصيلة والمسافة/المنطقة والتوفر الأولي.
3. تظهر إشعارات افتراضية؛ المتبرع يقبل أو يرفض.
4. تتغير عدادات **الاستجابات**؛ **لا تتغير** عدادات التبرعات المكتملة أو النقاط بهذا الإجراء.
5. المؤسسة تغلق الطلب أو تعتبره مستوفًى عند توثيق الوحدات المطلوبة وفق الإجراءات المعتمدة.

### D. تبرع مباشر أو مرتبط بطلب
1. يحضر المتبرع إلى بنك الدم؛ التبرع الطبي لا يشترط أن يكون لديه حساب حياة.
2. إن لم يكن مسجلًا، يساعده الموظف في فتح **الموقع العام على جوال المتبرع**؛ المتبرع يُدخل كلمة مروره ورمز تأكيد بريده بنفسه، وليس الموظف.
3. الموظف المخوّل يبحث عن حساب المتبرع من لوحة المؤسسة، ويختار `Record Donation`.
4. يوثق تاريخ التبرع والمؤسسة والحالة والطلب المرتبط **اختياريًا**.
5. عندما يُعتمد التبرع كـ`confirmed`، يسجّل النظام حركة **+5** مرة واحدة، ويحدّث سجل المتبرع وتقارير المؤسسة والإدارة.

### E. تصحيح سجلات النقاط
- لا يُسمح بمنح +5 مرتين لنفس سجل التبرع.
- لا يغيّر المتبرع رصيد نقاطه يدويًا.
- في حالة التوثيق الخطأ، تتم مراجعة السجل وإضافة حركة تصحيح موثقة بالسبب والفاعل، بدل حذف الأثر الرقابي.
- عدد الردود المقبولة وعدد التبرعات المؤكدة مقياسان مختلفان.

## 7. نموذج البيانات المنطقي المقترح (تعديل على ERD)

فصل الاستجابات عن التبرعات ضرورة منطقية بعد إضافة النقاط؛ وصف ERD في التقرير يجمع `DONATIONS / RESPONSES` في كيان واحد (القسم 3.5.4، صفحة PDF 37).

| الكيان | حقول/علاقات أساسية مقترحة |
|---|---|
| `users` | id, name, email, phone, role, status, email_verified_at, blood_type_id, city, area, location |
| `blood_banks` | id, name, contact, city, area, lat, lng, status |
| `bank_staff` | user_id, blood_bank_id, is_official_representative, status, created_by |
| `blood_types` | id, code؛ دعم `unknown` كحالة بيانات لا كفصيلة مطابقة |
| `blood_requests` | id, bank_id, blood_type_id, units_needed, units_fulfilled, urgency, radius, status, created_by |
| `donor_responses` | id, request_id, donor_id, status, responded_at |
| `donations` | id, donor_id, bank_id, request_id nullable, donated_at, confirmation_status, confirmed_by, confirmed_at |
| `point_transactions` | id, donor_id, donation_id, points_delta, type, reason, created_by, created_at |
| `notifications` | id, donor_id, request_id nullable, channel, status, created_at |
| `audit_logs` | id, actor_id, action, subject_type, subject_id, timestamp, details |

**ضوابط التصميم:** سجل `donations` من دون `request_id` يمثل تبرعًا مباشرًا؛ سجل منح النقاط مرتبط بتبرع فريد؛ الحساب البنكي مرتبط بمؤسسة محددة؛ الممثل الرسمي علامة صلاحية داخل المؤسسة، وليس Role رابعًا؛ تفاصيل رموز التحقق تُصمم آمنًا في الـBackend لاحقًا.

## 8. حالات البيانات (State Models)

- **حساب المتبرع:** `pending_verification → active`؛ ويمكن أن يصبح `suspended` بقرار إداري. الحساب غير المؤكد لا يدخل اللوحة.
- **طلب الدم:** `active → fulfilled` أو `active → cancelled`، كما ورد في UC-09.
- **استجابة الطلب:** `pending / accepted / declined`؛ وتتبع مستقل عن حالة التبرع.
- **التبرع:** `recorded / confirmed / corrected` كتصور تنفيذي؛ لا تمنح نقاط إلا لسجل مؤكد، مع تسجيل التصحيحات.
- **نقاط المتبرع:** مجموع حركات `point_transactions`، لا قيمة قابلة للتعديل المباشر بواسطة المتبرع.

## 9. ما يفعله Frontend MVP وما لا يفعله

| الوظيفة | Frontend MVP | المنتج الحقيقي |
|---|---|---|
| الواجهات والتنقل والتحقق من الحقول | يعمل | يعمل |
| حسابات نموذجية وتبديل الأدوار | محاكاة محلية | توثيق حقيقي وصلاحيات على الخادم |
| تفعيل البريد واستعادة كلمة المرور | Mock دون رسائل حقيقية | إرسال آمن وتوكنات صالحة مرة واحدة |
| طلبات الدم والاستجابات | بيانات JavaScript تجريبية | API + قاعدة بيانات مشتركة |
| المطابقة المكانية | بيانات إحداثيات/مناطق تجريبية | خوارزمية موثقة وبيانات موقع مصرح بها |
| نقاط التبرع والتصحيح | محاكاة في بيانات المتصفح | معاملات ذرّية وسجلات تدقيق على الخادم |
| Web Push وSMS | عرض إشعارات افتراضية | تكامل حقيقي مع خدمات الإشعارات |
| PWA/Offline | ممكن نموذج للكاش الثابت فقط | قدرات وتزامن مدروسة واختبارات انقطاع اتصال |
| تبديل الحساب بين جهازين | **غير متاح عبر localStorage** | ممكن بقاعدة بيانات مركزية |

**أمان الـMVP:** لا تُستخدم بيانات مرضى/متبرعين حقيقية، ولا كلمات مرور حقيقية في تخزين المتصفح، ولا يُقدَّم النموذج على أنه خدمة آمنة أو جاهزة للتشغيل في مستشفى.

## 10. متطلبات غير وظيفية من التقرير

## 11. معايير قبول نسخة الـMVP التجريبية

1. إنشاء حساب تجريبي يلزم الهاتف والبريد، ويمنع التكرار محليًا.
2. لا يظهر Donor Dashboard قبل إتمام التفعيل التجريبي.
3. تسجيل دخول تمثيلي يعرض واجهة الدور الصحيح ويمنع الوصول للواجهات غير المصرح بها على مستوى المحاكاة.
4. System Admin ينشئ مؤسسة وممثلها الرسمي.
5. الممثل يضيف موظفًا مرتبطًا بمؤسسته، والموظف لا يرى زر إدارة الموظفين.
6. موظف البنك ينشئ طلبًا؛ يظهر للمتبرع المطابق في نفس بيئة الاختبار المحلية.
7. قبول الطلب يغير عداد الردود فقط، دون زيادة التبرعات أو النقاط.
8. توثيق تبرع مرتبط بطلب يضيف +5 مرة واحدة ويُظهر السجل للمتبرع.
9. توثيق تبرع مباشر بلا طلب يضيف +5 مرة واحدة.
10. بعد تسجيل متبرع جديد من الصفحة العامة (على محاكاة جهازه)، يمكن ربط سجل تبرعه بالحساب في بيئة الاختبار.
11. تصحيح توثيق خاطئ يحدث حركة نقاط مقابلة مع تسجيل السبب.
12. كشف المؤسسة لا يتضمن تبرعات مؤسسة أخرى؛ لوحة الإدارة تعرض التجميع الشامل.
13. تجربة الهاتف والكمبيوتر متجاوبة، مع حالات فارغة وتحميل وأخطاء واضحة.

## 12. نقاط غير محسومة — لا نعتبرها قرارات نهائية

1. **المواعيد:** يذكر التقرير *Appointment Workflows* في الأهداف، لكن لا يوجد له FR أو UC مفصّل مستقل؛ هل نضيف شاشة حجز مواعيد فعلية؟
2. **تحديد هوية المتبرع وفصيلته:** كيف تؤكد الجهة الطبية الفصيلة قبل تفعيل المطابقة؟ وما حالة المستخدم الذي اختار «لا أعرف»؟
3. **التحقق بالبريد:** شكل OTP/الرابط، مدة الصلاحية، عدد المحاولات، ومهلة إعادة الإرسال.
4. **الموقع:** دقة الموقع المطلوبة، الاستئذان، وخطة البديل إذا رفض المستخدم تحديد الموقع.
5. **ضوابط توثيق التبرع:** مستند/رقم سجل مرجعي لمنع توثيق أو تكرار خاطئ في النسخة الحقيقية.
6. **تقارير الإدارة:** سياسة كشف هوية المتبرع في التقارير الصحية، ومن يحق له استلام ملف تفصيلي.
7. **إلغاء الطلب بعد استجابة متبرع:** طريقة إشعاره، ومعاملة الاستجابة السابقة.
8. **PWA Offline:** هل المطلوب قراءة صفحات مخزنة فقط أم إدخال تغييرات دون إنترنت مع مزامنتها لاحقًا؟

هذه البنود تُراجع قبل اعتماد الـSRS النهائي، ولا ينبغي الإيحاء بأن التقرير الأصلي حسمها.

## 13. مقترح تنظيم العمل قبل سبرنتات المنتج الحقيقي

### مرحلة الـFrontend Prototype — قبل تطوير Backend

- **WP-01 | UI Foundation:** تصميم موحد RTL، شريط التنقل، صفحات الدخول والتسجيل والتفعيل التمثيلي.
- **WP-02 | Donor Module:** صفحات المتبرع السبع، الطلبات والإشعارات، السجل والنقاط.
- **WP-03 | Blood Bank Module:** صفحات المؤسسة الثماني، إدارة الموظفين، إنشاء الطلبات، التبرعات المباشرة والنقاط.
- **WP-04 | System Admin + QA:** صفحات المدير السبع، التقارير، الاختبارات الشاملة وحالات الخطأ.

**شرط الخروج:** اجتياز سيناريوهات القبول الـ13 على بيانات تجريبية في نفس بيئة المتصفح، دون ادعاء تكامل حقيقي بين الأجهزة.

### سبرنتات التطوير الحقيقي — مقترح يحتاج اعتماد الفريق

التقرير الأصلي يقترح خمسة سبرنتات مدة كل منها أسبوعان: (1) المتطلبات وقاعدة البيانات؛ (2) التوثيق والصلاحيات؛ (3) الطلبات والمطابقة؛ (4) PWA وSMS/Push؛ (5) الاختبار. بعد توسع النطاق، يمكن اقتراح **ستة سبرنتات** بدل خمسة:

| Sprint | المخرجات |
|---|---|
| Sprint 1 | SRS/ERD نهائيان، قاعدة البيانات، البنية الأساسية والاختبارات الأولية |
| Sprint 2 | Authentication وRBAC، تفعيل البريد، المؤسسات والممثل والموظفون |
| Sprint 3 | طلبات الدم، المطابقة الأولية، الاستجابات، لوحات المتبرع والبنك |
| Sprint 4 | التبرعات المباشرة والمرتبطة، التأكيد، النقاط والتدقيق، كشوف المؤسسات |
| Sprint 5 | Push/SMS والتعامل مع فشل الإرسال، PWA وتجارب الاتصال المنقطع |
| Sprint 6 | التقارير الإدارية، اختبارات الأمان والقبول والأداء، تحسين الواجهات والإطلاق التجريبي |

**ملاحظة:** تقسيم السبرنتات الجديد *اقتراح تخطيطي* وليس قرارًا معتمدًا؛ ويجب تقدير الجهد وفق حجم الفريق وتوزيع المسؤوليات قبل تثبيت المدة.

## خلاصة القرارات

- **معتمد:** 3 أدوار رئيسية؛ ممثل رسمي واحد أو أكثر حسب سياسة المؤسسة، ينشئ System Admin الممثل الأول، والممثل يضيف موظفي مؤسسته، والموظفون لهم صلاحيات التشغيل نفسها ما عدا إدارة الموظفين.
- **معتمد:** هاتف وبريد إلزاميان للمتبرع، وتفعيل البريد قبل الدخول.
- **معتمد:** المتبرع غير المسجّل يُساعده الموظف على **جوال المتبرع في صفحة التسجيل العامة**، لا من لوحة البنك.
- **معتمد:** +5 نقاط عن كل تبرع فعلي مؤكد، سواء ارتبط بطلب داخل حياة أم لا؛ مع سجل وتصحيح وتقارير.
- **معتمد:** تقارير مشرف الصحة داخل لوحة System Admin، دون دور رابع.
- **غير معتمد بعد:** تفاصيل OTP الزمنية، حجز المواعيد، سياسات التحقق الطبي من بيانات الفصيلة، ومواصفات المزامنة دون اتصال.

## توضيح المستخدم لتدفق الاستجابة — 1 نوفمبر 2026

استجابة المتبرع لطلب محدد تربطه بتنسيق جارٍ واحد، وتُخفي النداءات الأخرى عنه مؤقتًا مع إمكانية التراجع. تظهر حالة «بانتظار التنسيق» بدل تكرار أزرار القبول، ولا يمكن قبول طلب ثانٍ قبل إنهاء الاستجابة الحالية. هذه حالة شخصية مستقلة عن حالة طلب المؤسسة الذي يستمر لباقي المتبرعين حتى إغلاقه. تُحفظ النداءات المخفية، وتُستأنف المطابقة الأولية بعد انتهاء التنسيق دون اختراع موعد أو فترة أهلية طبية، ودون تغيير تفضيل التوفر. القبول لا يمنح نقاطًا؛ تبقى +5 مرتبطة بتوثيق التبرع الفعلي فقط.
